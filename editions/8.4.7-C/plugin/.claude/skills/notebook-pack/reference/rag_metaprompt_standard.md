# 📐 RAG METAPROMPT STANDARD v2.0
# Универсальная инструкция по построению больших метапромтов под RAG

> Обновлено 2026-06-21. Принципы версии 1.0 сохранены полностью — они
> архитектурно-независимы. В §0 добавлена актуальная модель того, как
> на самом деле работают современные RAG-бэкенды (это важно для понимания,
> ПОЧЕМУ работают приёмы ниже).

═══════════════════════════════════════════════════════════════════
ПРИНЦИП-ФУНДАМЕНТ
═══════════════════════════════════════════════════════════════════

<!-- rag_anchor: core_principle -->

RAG-движок разрезает документы на чанки и возвращает наиболее
релевантные. Качество ответа LLM = качество попавших в контекст
чанков. Задача автора метапромта: сделать каждый чанк
самодостаточным, точно именованным и свободным от семантического
шума соседних концепций.

АНАЛОГИЯ: один чанк = один параграф в учебнике. Если на странице
смешаны три темы — студент не поймёт ни одну. Если каждая тема
на отдельной странице с заголовком — поиск точный.

КЛЮЧЕВОЕ ПРАВИЛО: один файл — одна семантическая зона.
Один параграф — одна концепция. Один тег — один сигнал.

§0. КАК НА САМОМ ДЕЛЕ РАБОТАЮТ RAG-БЭКЕНДЫ (актуально на 2026)
═══════════════════════════════════════════════════════════════════

<!-- rag_anchor: how_rag_backends_work -->

<rag_backend_model>

// Этот раздел объясняет ПОЧЕМУ работают все приёмы ниже.
// Важно не путать два разных механизма.

─── ДВА РАЗНЫХ МЕХАНИЗМА ───

  1. КЛАССИЧЕСКИЙ ЧАНК-RAG (retrieval по векторам)
     Документы режутся на чанки → эмбеддятся → кладутся в векторную БД.
     По запросу достаются ближайшие по смыслу чанки → попадают в промт.
     Так работают: enterprise-RAG, кастомные пайплайны, NotebookLM на
     большом корпусе.

  2. LONG-CONTEXT INGESTION (всё в окно)
     Источники целиком подаются в большое контекстное окно модели
     (сегодня это 1M токенов у фронтир-моделей). Retrieval не нужен,
     пока корпус помещается в окно.

─── ВАЖНОЕ УТОЧНЕНИЕ (развеиваем частый миф) ───

  Миф: "NotebookLM просто грузит весь блокнот в 1M-окно целиком".
  Факт: даже у моделей с 1M-окном бэкенд делает ВЫБОРКУ из источников
  под конкретный запрос, а не подаёт весь корпус в каждую генерацию.
  1M-контекст относится к ОДНОМУ чат-сеансу (история диалога + выбранные
  фрагменты), а не к "всему блокноту одновременно".

  Практический вывод: даже при гигантском окне retrieval-качество и
  размер окна — РАЗНЫЕ вещи. Большое окно НЕ гарантирует, что модель
  найдёт нужный факт в середине корпуса (см. §0.1 "Lost in the Middle").
  Поэтому структурирование источников под retrieval остаётся критичным
  на ЛЮБОМ бэкенде.

─── §0.1 ЭФФЕКТ "LOST IN THE MIDDLE" ───

<!-- rag_anchor: lost_in_the_middle -->

  Установленный факт (Liu et al., TACL 2024): модели лучше используют
  информацию в НАЧАЛЕ и в КОНЦЕ контекста и заметно хуже — в СЕРЕДИНЕ.
  Внимание распределяется U-образно (primacy + recency bias).

  Эмпирически подтверждается на свежих моделях: на длинных срезах
  (ближе к 1M токенов) точность извлечения из середины падает в разы
  даже у моделей, заявленных как "длинноконтекстные".

  СЛЕДСТВИЕ ДЛЯ АВТОРА МЕТАПРОМТА:
  - Критичные инструкции — в начало И в конец файла/секции, не в середину.
  - Подавать модели не "весь корпус", а отобранные релевантные фрагменты.
  - Чем точнее изолирован факт (frontmatter + якорь + короткая зона) —
    тем выше шанс, что он попадёт в выборку и в "сильную" зону внимания.

─── §0.2 ЧТО ДЕЛАЕТ RAG БОЛЕЕ НАДЁЖНЫМ ───

  Современные бэкенды (включая NotebookLM на актуальном Gemini) сверх
  базового retrieval умеют: гибридный поиск (по смыслу + по ключевым
  словам), реранкинг кандидатов, грунтинг с цитатами на конкретные
  места источника, и агентные проходы (несколько итераций поиска).

  Грунтинг + цитаты = главный механизм снижения галлюцинаций:
  ответ привязан к источнику, и его можно проверить кликом.

</rag_backend_model>

§1. СТРУКТУРА СИСТЕМЫ ФАЙЛОВ
═══════════════════════════════════════════════════════════════════

<!-- rag_anchor: file_structure -->

<file_architecture>

─── ОБЯЗАТЕЛЬНЫЕ ФАЙЛЫ ───

  00_INDEX.md        — Мастер-индекс всей системы (читается первым)
  00_CORE.md         — Конфигурация, identity, entrypoint
  01_ROUTER.md       — Маршрутизация запросов к модулям
  [02..N]_MODULE.md  — Тематические модули (один модуль = одна зона)

─── ПРИНЦИП НУМЕРАЦИИ ───

  00_*  — Системные файлы (config, index, routing)
  01_*  — Маршрутизация и оркестрация
  02-0N — Контентные модули (в порядке частоты обращений)
  [N-1] — Диагностика и troubleshooting
  [N]   — Шаблоны, рецепты, примеры

  Нумерация = приоритет RAG при конфликте чанков одинакового веса.
  Более низкий номер → выше приоритет.

─── ПРАВИЛО РАЗМЕРА ФАЙЛА ───

  Оптимум:    5 000 – 25 000 символов на файл
  Максимум:   50 000 символов (свыше — разбить на части A/B)
  Минимум:    1 000 символов (мельче не стоит — лучше объединить)

  Почему: RAG-чанкер обычно нарезает по 512–2048 токенов.
  Файлы >50K дают чанки с потерянным контекстом заголовка.

</file_architecture>

§2. YAML FRONTMATTER — ОБЯЗАТЕЛЬНЫЙ ЗАГОЛОВОК КАЖДОГО ФАЙЛА

<!-- rag_anchor: yaml_frontmatter -->

<frontmatter_standard>

// Первое, что читает RAG при индексации файла.
// Эквивалент "первых 20-30 слов" с максимальным весом.
// Без frontmatter RAG не знает, о чём файл, пока не дочитает его.

─── ОБЯЗАТЕЛЬНЫЙ ШАБЛОН ───

---
file_id: [УНИКАЛЬНЫЙ_ID_ФАЙЛА]
version: [X.Y]
role: [роль файла в системе одним словом]
scope: [предметная область — 3-7 слов]
rag_priority: [critical | high | medium | low]
description: >
  [1-2 предложения: ЧТО содержит файл и КОГДА его нужно читать]
key_concepts:
  - [концепция_1]
  - [концепция_2]
  - [концепция_3]
depends_on: [список file_id от которых зависит этот файл]
used_by: [список file_id которые ссылаются на этот файл]
---

─── ОБЪЯСНЕНИЕ ПОЛЕЙ ───

file_id          — Уникальный ключ для перекрёстных ссылок.
                   Используй везде вместо имени файла.
role             — Одно слово: config | router | engine | vocab |
                   adapter | troubleshoot | templates | index
scope            — Семантический scope для RAG-фильтрации.
rag_priority     — critical: всегда подгружается первым
                   high: подгружается при релевантных запросах
                   medium: подгружается при явном упоминании
                   low: подгружается только при прямом запросе
description      — Самый важный текст. RAG цитирует его первым.
key_concepts     — Массив: каждый элемент = отдельный retrieval-якорь.
depends_on       — Граф зависимостей. LLM понимает, что читать вместе.
used_by          — Обратные ссылки. Помогает RAG строить контекст.

─── ПРИМЕР ЗАПОЛНЕНИЯ ───

---
file_id: STYLE_ENGINE
version: 1.0
role: engine
scope: style_prompt_construction
rag_priority: critical
description: >
  Содержит формулу построения Style-промта (GMIV+P), библиотеку
  жанровых дескрипторов, правила гибридизации и конструктор персон.
  Читать при любом запросе на создание или улучшение Style-промта.
key_concepts:
  - GMIV_formula
  - Time_and_Place_rule
  - instrument_descriptors
  - persona_workshop
  - hybrid_genre_lab
  - production_environments
depends_on: [CORE, AUDIO_VOCAB]
used_by: [ROUTER, TEMPLATES]
---

</frontmatter_standard>

<!-- rag_anchor: master_index_spec -->

<master_index>

// 00_INDEX.md — самый важный файл системы для RAG.
// Должен быть ПЕРВЫМ в блокноте / списке источников.
// При любом общем запросе RAG найдёт его первым
// через общие ключевые слова системы.

─── ОБЯЗАТЕЛЬНЫЕ СЕКЦИИ INDEX ───

## SYSTEM MAP (таблица всех файлов)

| file_id | Назначение | Ключевые концепции | Когда запрашивать |
|---------|-----------|-------------------|------------------|
| CORE    | Конфигурация и identity системы | preloader, версии, команды | При настройке или вопросах об identity |
| ROUTER  | Маршрутизация запросов | intent detection, platform, depth | При неопределённом намерении |
| ...     | ...       | ...               | ...              |

Почему таблица, а не prose: RAG индексирует таблицы как
структурированные данные — каждая строка = отдельный retrieval-сигнал.

## DEPENDENCY GRAPH (граф зависимостей ASCII)

  CORE ──► ROUTER ──► MODULE_A ◄── VOCAB
                  ├──► MODULE_B
                  └──► MODULE_C ◄── MODULE_A

Граф позволяет LLM понять, какие файлы читать вместе,
не дожидаясь явного указания пользователя.

## VERSION FLAGS (флаги версий)

  Список: что нового в текущей версии + какой файл читать.
  Пример: "v2.0: новый алгоритм X — см. MODULE_A §3"

## QUICK QUERY MAP

  Часто задаваемые вопросы → file_id + секция.
  Пример:
  "Как сделать Y?" → MODULE_B §2
  "Что означает тег Z?" → VOCAB §4

</master_index>

<rag_zone_system>

// RAG-зоны — это инструмент изоляции семантических единиц
// внутри одного файла. Без них длинный параграф чанкуется
// произвольно, разрывая смысл.

─── XML-ТЕГИ КАК СЕМАНТИЧЕСКИЕ ГРАНИЦЫ ───

Каждую смысловую секцию оборачивать:

  <rag_zone id="[уникальный_id]">
  ... контент ...
  </rag_zone>

  id должен быть уникальным в пределах всей системы файлов,
  не только внутри файла.

─── HTML-КОММЕНТАРИИ КАК ЯКОРЯ ───

Перед каждым параграфом/таблицей:

  <!-- rag_anchor: [семантический_ключ] -->

  Ключ = то, что LLM ищет при запросе.
  Пример: <!-- rag_anchor: instrument_descriptors_guitars -->

  Якоря работают даже когда XML-теги не поддерживаются:
  HTML-комментарии читаются парсером, но не рендерятся в UI.

─── РАЗДЕЛЕНИЕ ТЕОРЕТИЧЕСКОГО И ПРИМЕРНОГО КОНТЕНТА ───

ПЛОХО (смешанный блок):
  ## Правило X
  Объяснение правила X.
  ✅ Пример 1
  ❌ Пример 2
  Дополнительное объяснение.
  ✅ Пример 3

ХОРОШО (изолированные блоки):

  ## §N.1 RULE: Теоретическое обоснование X
  <!-- rag_anchor: rule_X_theory -->
  Объяснение: почему правило X работает так.

  ## §N.2 EXAMPLES: Правильное применение X
  <!-- rag_anchor: rule_X_correct_examples -->
  ✅ Пример 1 → результат
  ✅ Пример 3 → результат

  ## §N.3 EXAMPLES: Типичные ошибки X
  <!-- rag_anchor: rule_X_wrong_examples -->
  ❌ Пример 2 → почему это неправильно

Почему: три запроса ("что такое X?", "покажи правильный пример X",
"покажи ошибку X") возвращают три точных чанка вместо одного
перегруженного.

─── ПРАВИЛО МАКСИМАЛЬНОЙ ДЛИНЫ СЕМАНТИЧЕСКОГО БЛОКА ───

  Один <rag_zone> = не более 50 строк / ~2000 символов.
  Если секция длиннее → разбить на §N.1, §N.2, §N.3...

</rag_zone_system>

§6. КОНТЕНТНЫЕ МОДУЛИ: ПРИНЦИПЫ ПОСТРОЕНИЯ
═══════════════════════════════════════════════════════════════════

<!-- rag_anchor: content_module_principles -->

<module_construction>

─── СТРУКТУРА СЕКЦИЙ ───

Каждый раздел модуля строится по схеме:

  ## §N. НАЗВАНИЕ КОНЦЕПЦИИ
  <!-- rag_anchor: [concept_key] -->

  <rag_zone id="[concept_key]">

  [1-2 предложения: что это и зачем]

  ─── ПРАВИЛА / ОПРЕДЕЛЕНИЯ ───
  [нормативный контент]

  ─── ПРИМЕРЫ ───
  [декларативный контент]

  ─── АНТИПРИМЕРЫ ───  (если применимо)
  [что НЕ делать]

  </rag_zone>

─── ТАБЛИЦЫ VS. PROSE ───

  ТАБЛИЦЫ для:
    - Маппинг (ключ → значение)
    - Сравнение (A vs B)
    - Справочники (параметр → эффект → пример)
    - Категоризированные списки

  PROSE для:
    - Объяснение причинно-следственных связей
    - Описание workflow с контекстом
    - Теоретические обоснования

─── ИМЕНОВАНИЕ СЕКЦИЙ ───

  Хорошие имена для rag_anchor (находимые по запросу):
    ✅ instrument_descriptors_guitars
    ✅ error_types_vocal_hallucination
    ✅ rule_brackets_theory
    ✅ template_recipe_edm

  Плохие имена:
    ❌ section_3 (не семантический)
    ❌ stuff (не специфичный)
    ❌ more_details (не находимый по теме)

─── ПРИОРИТЕТ ИНФОРМАЦИИ ВНУТРИ СЕКЦИИ ───

  Самое важное — в первые 2-3 строки секции.
  RAG обрезает чанки, а не секции. Хвост может потеряться.

  СТРУКТУРА ПРИОРИТЕТОВ:
  1. Определение / суть правила         ← всегда попадает в чанк
  2. Главный пример                     ← почти всегда
  3. Дополнительные примеры             ← часто
  4. Исключения и edge cases            ← иногда
  5. Исторический контекст / примечания ← редко нужен

</module_construction>

§7. ДЕДУПЛИКАЦИЯ: ЛИКВИДАЦИЯ СМЫСЛОВЫХ КЛОНОВ
═══════════════════════════════════════════════════════════════════

<!-- rag_anchor: deduplication -->

<deduplication_rules>

// Дублирование контента между файлами — главный враг RAG-точности.
// При запросе "что такое X?" RAG вернёт оба чанка с X, и они
// могут противоречить или дополнять друг друга непредсказуемо.

─── ПРАВИЛО ЕДИНОГО ИСТОЧНИКА ───

  Каждая концепция живёт РОВНО В ОДНОМ файле.
  В других файлах — только ССЫЛКА на первичный источник.

─── ФОРМАТ ССЫЛКИ (вместо дублирования) ───

  <!-- rag_ref: [file_id] §[N] [concept_key] -->
  > Полное описание: см. [file_id] §[N].
  > Краткая шпаргалка: [5-10 слов сути].

  Шпаргалка — допустима. Она не дублирует, а создаёт
  retrieval-якорь, который укажет на первичный источник.

─── ДОПУСТИМЫЕ ИСКЛЮЧЕНИЯ ───

  Дублирование разрешено ТОЛЬКО если:
  1. Это Quick Reference в INDEX-файле (не более 1-2 строк на пункт)
  2. Это автономный шаблон/рецепт (должен работать без обращения к другим файлам)
  3. Версионное различие (v1 и v2 одной концепции — разные файлы)

─── ДИАГНОСТИКА ДУБЛЕЙ ───

  При построении системы провести аудит:
  1. Выписать все key_concepts из всех frontmatter
  2. Найти повторяющиеся concepts → оставить в одном файле
  3. В остальных заменить на <!-- rag_ref: ... -->

</deduplication_rules>

§11. ВЕРСИОНИРОВАНИЕ СИСТЕМЫ
═══════════════════════════════════════════════════════════════════

<!-- rag_anchor: versioning -->

<versioning_strategy>

─── СТРАТЕГИЯ: ОТДЕЛЬНЫЙ БЛОКНОТ НА МАЖОРНУЮ ВЕРСИЮ ───

  Рекомендуется: отдельный NotebookLM/блокнот на каждую мажорную версию.

  Причина: при обновлении источников старые чанки остаются
  в индексе и конкурируют с новыми. Отдельный блокнот = чистый контекст.

  ИСКЛЮЧЕНИЕ: минорные версии (v1.1, v1.2) — обновление источников
  с тегом версии в frontmatter достаточно.

─── VERSION FLAGS В FRONTMATTER ───

  Каждый файл помечает свою версию:
  version: X.Y

  Это позволяет LLM отвечать "это правило из v1.0, актуальная
  версия v1.1 изменила его — см. §N.2"

─── CHANGELOG FILE ───

  Опционально: 00_CHANGELOG.md с таблицей:

  | Версия | Дата | Файл | Что изменилось |
  |--------|------|------|---------------|

  Особенно полезно при 20+ файлах: LLM понимает историю,
  не галлюцинируя устаревшие правила.

</versioning_strategy>

§12. ANTI-HALLUCINATION GUARDS
═══════════════════════════════════════════════════════════════════

<!-- rag_anchor: anti_hallucination -->

<anti_hallucination_guards>

// В source-grounded RAG-системах LLM должен явно сигнализировать,
// когда ответ выходит за рамки источников.

─── МАСТЕР-ПРОМТ GUARD (вставлять в custom instructions / system prompt) ───

  "Отвечай только на основе источников этого блокнота.
   Для каждого содержательного тезиса приводи цитату:
   [file_id, §N, rag_anchor].
   Если точной цитаты нет — напиши:
   'В источниках нет прямого ответа. Рассуждение основано
   на интерпретации [file_id]'.
   Любое утверждение без опоры на источник = ошибка."

─── GAP ANALYSIS ПРОМТ ───

  "Используя только источники этого блокнота, найди 3-5 категорий
   пробелов в документации по следующим осям:
   (а) концептуальные, (б) процедурные, (в) примерные.
   Для каждого пробела: описание + файлы с ближайшим контентом +
   формулировка вопроса к авторам.
   Оформи таблицей. Каждый тезис — с цитатой."

─── CONFLICT DETECTION ПРОМТ ───

  "Найди противоречия между источниками блокнота.
   Формат: [file_id_A §N] утверждает X,
           [file_id_B §M] утверждает Y.
   Предложи разрешение или пометь как 'открытый вопрос'."

─── ПОЗИТИВНЫЕ ФОРМУЛИРОВКИ (принцип Trigger Words) ───

  Описание проблемы в промте заставляет модель "представлять"
  проблему и усиливать её. Всегда формулировать позитивно:

  ❌ "не галлюцинируй", "избегай ошибок", "не придумывай"
  ✅ "отвечай только на основе источников"
  ✅ "каждый тезис сопровождай цитатой"
  ✅ "при отсутствии данных — явно укажи это"

</anti_hallucination_guards>

§13. ВОРКФЛОУ СОЗДАНИЯ НОВОЙ СИСТЕМЫ МЕТАПРОМТОВ ПОД RAG
═══════════════════════════════════════════════════════════════════

<!-- rag_anchor: creation_workflow -->

<creation_workflow>

STEP 1 — ОПРЕДЕЛИ СЕМАНТИЧЕСКИЕ ЗОНЫ (до написания)
  Выпиши все концепции системы.
  Сгруппируй по смысловой близости.
  Каждая группа = отдельный файл.
  Правило: если две концепции всегда нужны вместе → один файл.
  Если нужны независимо → разные файлы.

STEP 2 — ПОСТРОЙ ГРАФ ЗАВИСИМОСТЕЙ
  Нарисуй ASCII-граф: какой файл от какого зависит.
  Это станет depends_on / used_by в frontmatter
  и DEPENDENCY GRAPH в 00_INDEX.md.

STEP 3 — НАПИШИ 00_INDEX.md ПЕРВЫМ
  Заполни таблицу файлов (SYSTEM MAP) — даже если файлы пустые.
  Это твой "договор" с RAG-системой о том, что и где.

STEP 4 — НАПИШИ 00_CORE.md
  Preloader с конфигурацией.
  Quick Reference Rules (8-12 пунктов).
  Краткий file index.

STEP 5 — НАПИШИ 01_ROUTER.md
  Keyword → Module MAP (таблица).
  Intent → Output MAP (таблица).
  Depth calibration (таблица).
  БЕЗ псевдокода IF/ELSE.

STEP 6 — НАПИШИ КОНТЕНТНЫЕ МОДУЛИ
  Для каждого файла:
  a) Frontmatter
  b) Одна семантическая зона на файл
  c) RAG-зоны внутри (XML теги + HTML якоря)
  d) Разделить теорию и примеры
  e) Проверить: нет ли дублей с другими файлами?

STEP 7 — НАПИШИ TROUBLESHOOT ФАЙЛ
  Symptom Index таблица — первой.
  Затем детальные типы ошибок с зонами.

STEP 8 — НАПИШИ TEMPLATES ФАЙЛ
  Index table шаблонов — первой.
  Каждый шаблон — изолированная зона с тегами.

STEP 9 — АУДИТ ДУБЛИРОВАНИЯ
  Сравни key_concepts из всех frontmatter.
  Найди повторы → оставь в одном файле, в других → rag_ref.

STEP 10 — ТЕСТ В RAG-СИСТЕМЕ
  Загрузи в NotebookLM / Gemini Notebooks.
  Задай 10 тестовых вопросов разных типов.
  Проверь: цитаты точные? Правильный файл? Нет смешения?
  Если цитата "обрывается" — секция слишком длинная, разбей.

</creation_workflow>

§15. QUICK REFERENCE: ГЛАВНЫЕ ПРАВИЛА
═══════════════════════════════════════════════════════════════════

<!-- rag_anchor: quick_reference -->

<quick_rules>

1. ОДИН ФАЙЛ = ОДНА СЕМАНТИЧЕСКАЯ ЗОНА.
   Нельзя смешивать разные концепции в одном файле без изоляции.

2. FRONTMATTER — ОБЯЗАТЕЛЕН.
   Первые строки файла = максимальный RAG-вес. Без frontmatter
   RAG не знает, о чём файл.

3. 00_INDEX.md — ПЕРВЫЙ ФАЙЛ В БЛОКНОТЕ.
   Он определяет всю последующую навигацию RAG.

4. ТАБЛИЦЫ > ПСЕВДОКОД > PROSE для маппинга.
   Keyword → Module MAP всегда в виде таблицы.

5. НОЛЬ ДУБЛИРОВАНИЯ.
   Каждая концепция живёт в одном файле. Остальные — rag_ref.

6. SYMPTOM-FIRST в Troubleshoot.
   Таблица симптомов идёт первой, детали — после.

7. ТЕОРИЯ ОТДЕЛЬНО ОТ ПРИМЕРОВ.
   §N.1 = правило. §N.2 = правильные примеры. §N.3 = ошибки.

8. ШАБЛОНЫ — АВТОНОМНЫЕ ЗОНЫ.
   Каждый шаблон работает сам по себе, без ссылок на другие файлы.

9. ПОЗИТИВНЫЕ ФОРМУЛИРОВКИ В ПРОМТАХ.
   Называние проблемы = усиление проблемы. Описывай желаемое.

10. ТЕСТ = 10 РАЗНЫХ ЗАПРОСОВ.
    Система готова, когда каждый из 10 типов запросов возвращает
    точный, не загрязнённый чанк.

</quick_rules>
