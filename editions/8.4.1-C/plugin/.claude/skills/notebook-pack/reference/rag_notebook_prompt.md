# 🧩 RAG NOTEBOOK PROMPT v2.0
# Универсальный системный промпт для работы с метапромтами через RAG-блокнот

> Документ из двух частей.
> **Часть I** — готовый системный промпт (копировать в блокнот / custom instructions).
> **Часть II** — рабочая инструкция: механика, якорение, лайфхаки, лимиты, паттерны.
> Все факты актуальны на июнь 2026. Примеры — нейтральные, под любой проект.

═══════════════════════════════════════════════════════════════════
ЧАСТЬ I. ГОТОВЫЙ СИСТЕМНЫЙ ПРОМПТ (КОПИРОВАТЬ КАК ЕСТЬ)
═══════════════════════════════════════════════════════════════════

<!-- rag_anchor: ready_system_prompt -->

Ниже — самодостаточный системный промпт. Вставлять в поле системных
инструкций блокнота (в NotebookLM — настраиваемый промт; в Gemini —
инструкции ноутбука; в Claude Project — Project instructions).
Заменить значения в [квадратных скобках] под свой проект.

```text
# PERSONA
Ты — [роль: например, ведущий инженер/аналитик/автор документации]
по системе [НАЗВАНИЕ_СИСТЕМЫ vX.X]. Ты работаешь ТОЛЬКО с источниками
этого блокнота. За пределы загруженных материалов не выходишь без
явного разрешения пользователя.

# TASK_ANCHOR: [уникальный_ID_задачи]
[Конкретная цель в 1–2 предложениях. Что именно нужно получить
на выходе и зачем.]

# CONTEXT_SCOPE
Источники: опирайся на файлы/теги [перечислить ключевые .md-файлы
или теги, релевантные задаче].
Разрешено: синтез, сопоставление источников, цитирование с указанием
файла и раздела, выявление противоречий между источниками.
Ограничения: не домысливай и не интерполируй за пределами источников;
не подменяй факты из источников собственными общими знаниями;
если используется веб-поиск — явно отделяй веб-данные от данных блокнота.

# OUTPUT_CONTRACT
Формат: [таблица / маркированный список / параграфы — выбрать].
Объём: [лимит, например «до 400 слов» или «таблица на 7–10 строк»].
Цитирование: каждый содержательный тезис сопровождай ссылкой вида
[файл, §раздел].
Язык ответа: [русский / украинский / другой].

# ANTI_HALLUCINATION_GUARD
Отвечай на основе источников блокнота.
Если точной опоры в источниках нет — прямо пиши:
«В источниках нет прямого ответа по [тема]; ниже — интерпретация на
основе [файл]» — и помечай такой фрагмент.
Любое утверждение без опоры на источник считается ошибкой.
Если вопрос выходит за рамки блокнота — предложи уточнить запрос или
добавить недостающие источники.
```

КОМПАКТНАЯ ОДНОСТРОЧНАЯ ВЕРСИЯ (для разовых чат-запросов):

```text
Роль: [роль] | Задача: [задача] | Контекст: только источники блокнота,
без домысливания | Формат: [вывод] + цитата [файл, §] на каждый тезис |
Если данных нет — скажи прямо, не выдумывай.
```

ПОЧЕМУ ИМЕННО ЭТА СТРУКТУРА:
Структурированный запрос (Persona / Task / Context / Output / Guard)
даёт заметно более точный и проверяемый результат, чем «поисковая»
формулировка одним предложением. Это и есть главное отличие работы
с grounded-бэкендом от свободного чата с обычной LLM.

ЧАСТЬ II. РАБОЧАЯ ИНСТРУКЦИЯ
═══════════════════════════════════════════════════════════════════

───────────────────────────────────────────────────────────────────
§1. МЕХАНИКА: ЧТО ТАКОЕ "GROUNDED-БЭКЕНД" И КАК ОН РАБОТАЕТ
───────────────────────────────────────────────────────────────────

<!-- rag_anchor: grounded_backend_mechanics -->

Базовая идея связки «блокнот + чат»: блокнот (NotebookLM) выступает
заземлённым бэкендом (grounded backend) с проверяемыми источниками и
точным цитированием, а чат-модель (Gemini / Claude) даёт рассуждения,
синтез и — при необходимости — веб-поиск.

ДВА РЕЖИМА, КОТОРЫЕ НАДО РАЗЛИЧАТЬ:

1. ВНУТРИ САМОГО NotebookLM — ответ СТРОГО привязан к источникам
   (source-grounded), веб в ответ по умолчанию не вмешивается, каждый
   тезис сопровождается inline-цитатой на конкретное место источника.

2. БЛОКНОТ, ПРИКРЕПЛЁННЫЙ К ЧАТУ Gemini — ответ привязан к источникам
   блокнота, НО модель МОЖЕТ дополнительно подключать веб-поиск и другие
   инструменты. Это «лучшее из двух миров»: грунтинг блокнота + свобода
   и актуальность чата. Минус — без явного guard модель может подмешать
   «от себя».

ВАЖНО ПРО КОНТЕКСТ (развеиваем миф):
Даже при окне в 1M токенов бэкенд НЕ «грузит весь блокнот целиком»
в каждый ответ. Под конкретный запрос делается выборка релевантных
фрагментов, плюс история текущего чат-сеанса. 1M-контекст относится
к ОДНОМУ сеансу, а не ко «всему блокноту одновременно». Поэтому
структура источников под retrieval критична на любом объёме.

ДВУНАПРАВЛЕННАЯ СВЯЗКА (Notebooks в приложении Gemini):
Источники, добавленные в одном приложении, появляются в обоих.
Чат, проведённый в контексте блокнота, может индексироваться обратно
в блокнот как отдельный источник — это даёт самообучающийся слой
памяти: черновики и выводы из чата становятся материалом для следующих
запросов. (Точную глубину учёта истории всех чатов Google не
документирует — см. §6 «Открытые вопросы».)

───────────────────────────────────────────────────────────────────
§2. КАК СТРОИТЬ МЕТАПРОМТЫ ДЛЯ БОЛЬШОГО ЧИСЛА ИСТОЧНИКОВ
───────────────────────────────────────────────────────────────────

<!-- rag_anchor: metaprompt_structure -->

Главный принцип: СТРУКТУРА ВАЖНЕЕ ДЛИНЫ. Метапромт, который живёт как
источник (.md-файл), может быть многословным; но сами запросы к чату
держи краткими, опираясь на этот мастер-промт.

КАРКАС МЕТАПРОМТА (тот же, что в Части I):
PERSONA → TASK → CONTEXT/SCOPE → OUTPUT_CONTRACT → ANTI_HALLUCINATION_GUARD.

РЕКОМЕНДАЦИИ ПО ФАЙЛОВОЙ ОРГАНИЗАЦИИ:
- Вынеси каркас в отдельный файл _MASTER_PROMPT.md и используй его как
  системный промт блокнота.
- Дроби корпус по смысловым компонентам (один файл = одна зона), а не
  держи один гигантский файл — даже если лимит по словам позволяет.
- Заводи _GLOSSARY.md с определениями терминов экосистемы: модель
  использует его как терминологический якорь при синтезе между модулями.

БАЛАНС ЖЁСТКОСТИ GUARD-ПРАВИЛ:
Слишком жёсткие запреты («никогда не делай X») иногда снижают
полезность и креативность ответов. Для строгих доменов (право, финансы,
безопасность) — жёсткий guard оправдан; для исследовательских и
креативных задач — мягче. Формулируй правила ПОЗИТИВНО (см. §5).

───────────────────────────────────────────────────────────────────
§3. ВНУТРЕННЕЕ ЯКОРЕНИЕ И СВЯЗИ МЕЖДУ ФАЙЛАМИ
───────────────────────────────────────────────────────────────────

<!-- rag_anchor: internal_anchoring -->

Когда источников много (десятки файлов), модель теряет связность.
Самая частая ошибка — отсутствие якорных идентификаторов между файлами.
Устойчивые паттерны:

1. ID-ТЕГ В НАЧАЛЕ КАЖДОГО ФАЙЛА (HTML-комментарий, не рендерится в UI):
   <!-- SOURCE_ID: [ID] | VERSION: [vX.X] | DEPENDS_ON: [другой_ID] -->
   Модель читает такие комментарии в Markdown и использует при синтезе.

2. ФАЙЛ-ИНДЕКС _INDEX.md С КАРТОЙ ЗАВИСИМОСТЕЙ:
   таблица «ID источника → назначение → связанные файлы».
   Помогает строить связные ответы при приближении к лимиту источников.

3. ПЕРЕКРЁСТНЫЕ ССЫЛКИ В ТЕКСТЕ:
   явные отсылки вида [см. CHANGELOG vX.X §3] повышают вероятность, что
   оба связанных документа попадут в контекст одного ответа.

4. СЕМАНТИЧЕСКИЕ ТЕГИ В КОНЦЕ ИСТОЧНИКА:
   ## TAGS: [тема1], [тема2], [тема3]
   дают модели якоря для тематической фильтрации и быстрых «topic-промтов»
   («покажи все шаги, помеченные тегом [тема]»).

(Подробный стандарт разметки — frontmatter, rag_zone, rag_anchor,
rag_ref, дедупликация — вынесен в отдельный документ
RAG_METAPROMPT_STANDARD v2.0.)

ОТКРЫТЫЙ ВОПРОС: Google не раскрывает точный алгоритм приоритизации
источников/чанков (по размеру, давности, типу файла). Нет официального
подтверждения, что YAML/HTML-метаданные обрабатываются иначе, чем
обычный текст, — но эмпирически они помогают упорядочить выборку.

───────────────────────────────────────────────────────────────────
§4. ВОРКФЛОУ И ЛАЙФХАКИ (проверенные практики сообщества)
───────────────────────────────────────────────────────────────────

<!-- rag_anchor: workflows_lifehacks -->

ВОРКФЛОУ «RESEARCH POD» / SECOND BRAIN:
1. Ingest — собери все материалы (PDF, .md, транскрипты, заметки)
   в один блокнот.
2. Orchestrate — в чате с привязанным блокнотом попроси построить
   «карту знаний» (Research Map): темы, вопросы, пробелы.
3. Synthesize — чат-модель дополняет картину свежими веб-данными
   (что вышло после даты твоих источников); блокнот используешь как
   «корректор галлюцинаций» — верификатор по источникам.
Дешёвая альтернатива кастомному enterprise-RAG: получаешь веб-доступ
и reasoning чат-модели плюс гарантированные цитаты и закрытость блокнота.

ИТЕРАТИВНЫЙ АПГРЕЙД ПРОМТОВ (петля самоулучшения):
блокнот вытягивает материал по теме → другая LLM (например, Claude)
переписывает его в универсальный шаблон метапромта по RAG-стандартам →
шаблон возвращается в блокнот как мастер-промт. Удобно для миграции
и сравнения версий между собой.

ПРЕДОБРАБОТКА ИСТОЧНИКОВ ПЕРЕД ЗАГРУЗКОЙ:
прогони «грязный» текст через LLM с инструкцией «структурируй в Markdown
с заголовками, убери шум, добавь метаданные». Качество ответов RAG-бэкенда
кратно растёт на чистых, структурированных источниках.

ВЕРСИОНИРОВАНИЕ БЛОКНОТОВ — две стратегии:
- Версия = отдельный блокнот (рекомендуется для крупных версий):
  меньше риск засорить контекст старыми чанками; чистая выборка.
- Версия = теги/файлы MIGRATION + CHANGELOG в одном блокноте:
  удобно для сквозного поиска по всему стеку, но нужно строго следить
  за тегами и пометками версий.
Частый выбор: отдельный блокнот на мажорную версию + один «мета-блокнот»
с общим глоссарием и архитектурой.

«CHATS FROM GEMINI» КАК СЛОЙ ПАМЯТИ:
поскольку чат с привязанным блокнотом может индексироваться обратно
как источник, используй это как самообучающийся слой: черновики и
анализ из чата автоматически становятся материалом, который блокнот
потом проверяет на ошибки и противоречия.

───────────────────────────────────────────────────────────────────
§5. ПАТТЕРНЫ ПРОМПТОВ (готовые, нейтральные шаблоны)
───────────────────────────────────────────────────────────────────

<!-- rag_anchor: prompt_patterns -->

ПОЗИТИВНЫЕ ФОРМУЛИРОВКИ (базовый принцип):
Описание проблемы в промте заставляет модель «представлять» проблему.
Формулируй желаемое, а не запреты.
  ❌ «не галлюцинируй», «избегай ошибок», «не придумывай»
  ✅ «отвечай только на основе источников»
  ✅ «каждый тезис сопровождай цитатой»
  ✅ «при отсутствии данных — явно укажи это»

─── 5.1. GAP ANALYSIS (поиск пробелов в документации) ───

«Используя только источники этого блокнота, найди 3–5 категорий
пробелов по осям: (а) концептуальные, (б) процедурные, (в) примерные.
Для каждого пробела:
1) описание проблемы одним предложением;
2) файлы/разделы, где пробел особенно заметен;
3) 1–2 уточняющих вопроса к авторам.
Оформи таблицей. Каждый тезис — с цитатой [файл, §].»

─── 5.2. RECURRING TOPICS / ГЛОССАРИЙ ───

«Проанализируй источники, связанные с [версия/тег].
Определи 10–15 часто встречающихся понятий (модули, протоколы, режимы).
Для каждого:
1) короткое определение своими словами;
2) файлы, где встречается, с краткой цитатой;
3) есть ли противоречия между источниками.
Представь таблицей — это станет основой _GLOSSARY.md.»

─── 5.3. CONFLICT DETECTION (поиск противоречий) ───

«Найди противоречия между источниками блокнота.
Формат: [файл_A §N] утверждает X, [файл_B §M] утверждает Y.
Предложи разрешение или пометь как “открытый вопрос”.»

─── 5.4. RESEARCH MAP (карта тем для нового участника) ───

«Роль: аналитик системы [НАЗВАНИЕ] с доступом к блокноту.
Задача: построить карту тем, вопросов и рисков по [область].
Контекст: используй источники блокнота; при необходимости — веб-поиск,
но чётко отделяй веб-данные от данных блокнота; не давай финальных
рекомендаций по безопасности, только обозначай зоны риска.
Формат: сначала список 7–10 главных тем; затем по каждой —
(а) описание, (б) связанные источники, (в) открытые вопросы.
Язык: [язык].»

─── 5.5. CITATION-FORCING GUARD (для mixed-режима блокнот+веб) ───

«Отвечай на основе источников блокнота. Для каждого тезиса приведи
минимум одну цитату [файл, §]. Если точной цитаты нет — напиши:
“В источниках нет прямого ответа — рассуждение на основе интерпретации”.
Утверждения без опоры на источники считаются ошибкой.»

КОНСЕНСУС ПО ПАТТЕРНАМ:
- Лучшие промты для grounded-бэкенда ПРИНУЖДАЮТ к цитированию,
  структурируют вывод и явно обозначают границы источников — этим они
  отличаются от стиля «рассуждай свободно».
- Для больших проектов эффективнее СТЕК из нескольких связанных промтов
  (extract → analyze → synthesize), чем один «мега-промт на всё».

§6. КВОТЫ, ЛИМИТЫ И СКРЫТЫЕ ОГРАНИЧЕНИЯ (NotebookLM, июнь 2026)
───────────────────────────────────────────────────────────────────

<!-- rag_anchor: quotas_limits -->

ФОРМАЛЬНЫЕ ЛИМИТЫ NotebookLM ПО ТАРИФАМ:

| Параметр                | Free      | Plus / AI Pro | Ultra      |
|-------------------------|-----------|---------------|------------|
| Источников на блокнот   | 50        | 300           | 600        |
| Блокнотов всего         | 100       | 500           | 500+       |
| Слов на источник        | 500 000   | 500 000       | 500 000    |
| Размер файла (макс.)    | 200 МБ    | 200 МБ        | 200 МБ     |
| Чат-запросов в день     | ~50       | до ~500       | до ~5000   |
| Audio/Video Overviews/д | ~3        | больше        | ~200       |
| Deep Research           | ~10/мес   | ~20/день      | ~200/день  |

ПРИМЕЧАНИЯ:
- Лимит 500 000 слов на источник ОДИНАКОВ на всех тарифах (≈650–700
  страниц PDF). Технически один файл может вместить огромный корпус, но
  дробление по смыслу + якоря дают точнее retrieval, чем «простыня».
- Точные дневные числа Google периодически меняет и не всегда публикует
  единым списком — сверяйся с support.google.com/notebooklm перед
  планированием тяжёлых нагрузок.
- Цены тарифов привязаны к пакетам Google AI (Pro / Ultra) и меняются —
  актуальную цену проверяй на момент использования, не закладывай в гайд
  жёстко.

СКРЫТЫЕ / ЭМПИРИЧЕСКИЕ ОГРАНИЧЕНИЯ (по наблюдениям, не из официальных док):
- Внутренний «взвешенный» расход запросов: один тяжёлый запрос с большими
  файлами или контекстом >100K токенов может «стоить» нескольких обычных.
- Высокий thinking-уровень съедает заметную долю выходного бюджета на
  «размышления», уменьшая полезную длину ответа; UI это не показывает.
- В часы пик возможен тихий даунгрейд старшей модели на младшую и рост
  ошибок 429/503, при этом интерфейс может продолжать показывать старшую.
  Эмпирические обходы: запускать тяжёлое в off-peak, дробить запросы,
  reset чата или перенос в новый блокнот при «дрейфе темы».
  (Все цифры расхода — оценочные/наблюдательные, не гарантированные.)

КОНТЕКСТ НА УРОВНЕ ЧАТА vs БЛОКНОТА:
1M-контекст относится к одному чат-сеансу (выборка фрагментов + история
диалога), а не «весь блокнот в каждую генерацию». Это типично для
long-context: доступен большой буфер, но в него помещается выборка.

КОНСЕНСУС ПО ЛИМИТАМ:
- Предел в 50 источников (Free) для серьёзных проектов быстро становится
  узким — power-юзеры переходят на Plus/Pro ради 300 источников.
- Deep Research — более узкое горлышко, чем чат-запросы; берегите его
  под действительно тяжёлые задачи.
